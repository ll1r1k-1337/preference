# UI преферанса — стол, торговля, прикуп, вист и лист записи

Рабочий интерфейс для игры человека против двух ботов. Полностью на русском.

**Главное правило слоя:** UI не содержит игровой логики. Что легально —
решает движок (`src/engine`), сколько записать — модуль расчёта
(`src/scoring`). Интерфейс только рисует состояние и отправляет команды.

## Запуск

```bash
npm install
npm run dev        # http://localhost:5173
npm run gate       # tsc --noEmit + vitest run (289 тестов)
npm run build      # production-сборка в dist/
```

## Что делает слой партии (и почему он нужен)

Движок не знает истории партии, модуль расчёта — состояния раздачи. Между
ними ровно три вещи, и все они здесь:

1. **Ротация сдающего** — `nextDealer` после каждой раздачи.
2. **Счётчик распасов подряд** (§8.4) — растёт только на распасах,
   сбрасывается любой сыгранной раздачей, передаётся в
   `createDeal({ consecutiveRaspasy })`.
3. **`currentPool` до раздачи** (§9.8) — без него «американская помощь»
   молча не сработает и лист разойдётся с правилами (TS-44).

Склейка типов `PlayerId`: у движка это место за столом (`0 | 1 | 2`), у
`scoring` — строка. Приведение живёт в одной функции `toScoringOutcome`.

## Лист записи («пулька»)

`buildSheet(party)` — единственный источник для таблицы. UI ничего не
пересчитывает: строки берутся из `ScoreDelta` раздач, итоги — из накопленного
`Scoreboard`, финальный столбец — из `finalize`.

Учтены ловушки из хендоффа `scoring`:

* три дельты всегда, даже нулевые — на них держится выравнивание строк;
* `vistsOn` содержит только ненулевые ключи, читается как `?? 0`;
* `pool` / `mountain` — приращения (≥ 0), накопленный счёт только из `Scoreboard`;
* на мизере колонки вистов пустые (§7.7);
* сумма итогов по трём игрокам всегда 0 — это проверяется тестом.

Величина пули (§9.8) выбирается в шапке: 4 / 6 / 10 / 20.

## Пять мест, где UI обычно ошибается — как закрыты здесь

1. **Мизер проскакивает `WHIST_DECLARATION`** — диалог виста рисуется только
   в этой фазе, поэтому на мизере он не появляется вообще.
2. **`toAct` ≠ владелец карт.** При висте всветлую рука берётся по
   `play.toPlay`, а кнопки вешаются на `toAct`; в `renderHand` это разведено
   явно, с подписью «Вы ходите за: …».
3. **Распасы требуют `START_PLAY`.** Кнопки для этого нет — фазу продвигает
   `settle()` в `flow.ts`. Вскрытая карта прикупа показана над столом.
4. **«На своих» — розыгрыша нет** (`play === null`), сразу экран итога;
   стол в этом случае рисует фазу без взяток.
5. **Отказ — не исключение.** `dispatch` возвращает `{ ok: false, error }`,
   и `message` показывается подсказкой как есть, со ссылкой на параграф.

## Проверка

`npm run gate` — 289 тестов, `tsc --noEmit` чист.

**`src/game/__tests__/sheet.test.ts` (12 тестов)** — лист записи против
модуля `scoring` на полной партии: каждая строка сверяется с независимо
пересчитанным `scoreDeal`, итоги — с накопленным `Scoreboard`, финал — с
`finalize` и нулевой суммой.

**`src/ui/__tests__/ui-e2e.test.ts` (7 тестов)** — сквозная приёмка **через
настоящий DOM**: тест не вызывает движок, а кликает те же кнопки и карты,
что видит человек. Покрыто:

* полная пуля от раздачи до итогового пересчёта §9.9 (сумма итогов = 0);
* минимум 3 раздачи в листе записи;
* торговля, прикуп и снос вручную (в руке 12 карт до сноса);
* подсветка: кликабельны только `legalMoves`, остальные карты `disabled`;
* сохранение партии в localStorage вместе с выбранной величиной пули.

Ядро, движок и модуль расчёта не менялись: 22/22 файла совпадают по sha256 с
воркспейсами родительских задач.
